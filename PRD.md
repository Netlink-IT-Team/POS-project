## 6. Role-Based Access Control (RBAC)

* **Visitor / Public**
  * *Access*: Interactive web page (browse menu, find nearest booths, play games, and redeem points).
  * *Restrictions*: Zero access to POS, checkout API, or administrative dashboards.
* **Booth Worker (Kasir)**
  * *Access*: POS interface (QRIS & cash payment), local stock monitoring, and low-stock alerts for their assigned booth.
  * *Restrictions*: Cannot view global revenue, other booths' data, or system settings.
* **PIC (Operations Manager)**
  * *Access*: Global monitoring dashboard; full visibility to track revenue and stock levels across all 532 booths in Java.
  * *Restrictions*: Cannot modify backend code, database schemas, or low-level configurations.
* **Super Admin**
  * *Access*: Full system control (backend, database, user management, game/point configs, and deployment logs).
  * *Restrictions*: None.

## 7. Offline Mode & Data Sync

* **Local Storage First**
  * *Mechanism*: Transactions, local stock changes, and offline logs are saved locally (IndexedDB/SQLite) when internet drops across the booths[cite: 2].
  * *Behavior*: POS app keeps running smoothly without freezing or failing during poor network conditions.
* **Background Synchronization**
  * *Mechanism*: Auto-syncs the transaction queue to the Go backend and Supabase once a stable internet connection is restored[cite: 2].
  * *Conflict Resolution*: Server-side timestamp validation and transaction idempotency keys to prevent double-deduction or stock mismatch.

## 8. Backend Performance, Security & Concurrency Control

* **Rate Limiting**
  * *Mechanism*: Implemented in the Go backend (using Redis / Token Bucket algorithm).
  * *Purpose*: Protects auth, payment generation, and game point-redemption endpoints from bot spam, script automation, and abuse across the public web page.
* **Race Condition Prevention**
  * *Mechanism*: Strict database-level transaction isolation, row-level locking (`SELECT ... FOR UPDATE`), and idempotency keys for financial transactions & stock deductions.
  * *Purpose*: Prevents double-spending, negative inventory, or double-redemption of promo items when multiple booth workers or users hit the API simultaneously.
* **Caching Strategy**
  * *Mechanism*: Redis-based caching layer for semi-static data (e.g., menu items, nearest booth coordinate lists, game configurations).
  * *Purpose*: Reduces direct read load on Supabase and keeps API response times fast across all booths in Java.

## 9. Payment Gateway & Transaction Idempotency

* **Provider**: Xendit (API integration for dynamic QRIS generation).
* **Payment Flow**:
  * Cashier triggers checkout -> Go backend requests dynamic QRIS string/image via Xendit API -> Displayed on POS (Tablet/Web).
  * Webhook listener receives real-time payment confirmation status from Xendit and updates order status.
* **Idempotency Control (Double Settlement Prevention)**:
  * *Mechanism*: Every checkout request must include a unique client-side **Idempotency Key** (UUID) generated by the POS app.
  * *Execution*: Go backend checks this key in Redis/Database before processing settlement or inventory deduction. If a request with the exact same key arrives twice (due to network retries, double taps, or webhook duplicates), the backend safely ignores the second hit and returns the cached success response—preventing double charges and inventory bugs.
